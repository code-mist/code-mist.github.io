> 记录时间：2026年11月5日
> 设备：个人 Windows PC
> 核心问题：下载仿冒软件后 WDAC 策略被恶意部署，Defender 核心服务 `WinDefend` 被系统级拦截

---

## 一、起因：一次“没有细看”的下载

事情的起点很简单：我需要一个软件，在搜索引擎里找到了 `dashi-wangyi.com.cn` 这个域名，没有仔细核对，就下载了安装包。文件名看起来“有点问题”，但我还是运行了它。

事后回看，域名 `dashi-wangyi` 拼写本身就带着明显的仿冒痕迹，模仿的是“网易”相关产品。而我当时没有停下来多想一步。

下载站仿冒并不是新鲜事，但针对**网易云**这类中文用户高频软件的钓鱼活动，在 2025 年至 2026 年期间规模相当大。安全公司披露的黑客组织 **Silver Fox（银狐）** ，自 2023 年 6 月以来注册了超过 **2800 个**用于传播 Windows 恶意程序的域名，仿冒对象涵盖网易云音乐、爱思助手、Chrome、小红书、WPS 等数十款常用软件。我下载的那个站点，从命名特征和后果来看，与这一攻击模式高度吻合。

---

## 二、异常出现：风扇先“报警”

运行那个安装包之后，最先引起我注意的不是弹窗，也不是蓝屏，而是**风扇**。

电脑的风扇开始莫名其妙地高速运转，CPU 占用率明显升高，而且持续不降。这不是打开大型程序时那种有明确原因的负载，而是一种“机器在背着我干活”的感觉。

我意识到问题可能出在那个刚运行过的文件上。

事后对照安全厂商总结的 Silver Fox 感染征兆，这一条几乎是教科书式的： **“在排除硬件故障且用户没有主动运行大型应用程序的情况下，电脑的性能突然严重下降且系统资源占用率长时间居高不下”** ，应被视为高度可疑信号。木马释放的后门程序在后台运行，才让风扇先替我“喊了出来”。

---

## 三、排查：从“服务停止”到锁定 WDAC

我第一时间想到了 Windows Defender。打开安全中心，看到的是一行红色提示：**“威胁服务已经停止”**。

点击“立即重启”修复，报错；走关机流程重启，问题依旧。

接下来是一轮系统的排查，按顺序做了这些事：

| 步骤                    | 操作                                           | 结果                                         |
| ----------------------- | ---------------------------------------------- | -------------------------------------------- |
| 确认权限                | `fltmc` / `IsInRole` 检测                      | 管理员权限正常                               |
| 查询安全中心服务        | `sc.exe query wscsvc`                          | `RUNNING`                                    |
| 检查 Defender 全套服务  | `Get-Service WinDefend, WdFilter, WdNisSvc...` | **`WinDefend` 和 `WdNisSvc` 均为 `Stopped`** |
| 尝试启动 `WinDefend`    | `Start-Service WinDefend`                      | 失败，报错笼统                               |
| 尝试运行 `MpCmdRun.exe` | `MpCmdRun.exe -ResetPlatform`                  | **“应用程序控制策略已阻止此文件”**           |

最后那条报错是整个排查的转折点。“应用程序控制策略”指向的不是权限问题，不是文件损坏，而是 **WDAC（Windows Defender Application Control）** —— Windows 用来控制“哪些代码可以在内核层面运行”的机制。Defender 自己的核心组件 `MpCmdRun.exe` 被它拦住了。

---

## 四、根因：一条伪装成“微软官方”的 WDAC 策略

`CiTool.exe --list-policies` 的输出揭开了底牌。策略列表里有一条：

```
策略 ID: a244370e-44c9-4c06-b551-f6016e563076
好记的名称: AllowMicrosoft_2023-05-04
策略已签名: false
当前强制执行: true
```

名称伪装成微软风格，**“策略已签名: false”** 说明它没有被微软签名，是一条**未签名的恶意策略**。正是它在系统启动早期就加载并生效，把 `MsMpEng.exe`、`MpCmdRun.exe` 等 Defender 核心文件列入黑名单，导致 `WinDefend` 根本无法启动。

这不是孤例。微软社区中有用户报告了**完全相同策略 ID（`a244370e-44c9-4c06-b551-f6016e563076`）** 的 Trojan 感染案例，同样表现为 Defender 被禁用、服务无法启动。WDAC 滥用已经从理论威胁变成了在真实攻击中被反复使用的技术：攻击者在 `C:\Windows\System32\CodeIntegrity\` 下投放 `SiPolicy.p7b`，在 Defender 启动之前就用系统自己的代码完整性机制把它“锁死”。

---

## 五、修复过程（含一次启动故障）

### 5.1 第一次尝试与意外

最初的思路是处理 `SiPolicy.p7b`。我将其备份后删除，并创建了一个同名文件夹占位。但重启后系统无法正常启动，进入了 **“Preparing automatic repair”** 界面。

这说明在 `SiPolicy.p7b` 仍然被某种机制引用或保护的情况下，单纯移走文件会破坏启动链的完整性。最终通过 **系统还原** 回到了一个可启动的时间点。代价是此前对策略文件所做的改动被回滚，但换来的是进入系统的能力。

### 5.2 转向精准移除

系统恢复后，`WinDefend` 依然 `Stopped`，但 `CiTool` 仍然可用。这次不再动文件，而是用 `CiTool` **从策略管理层移除**：

```powershell
CiTool.exe -rp "{a244370e-44c9-4c06-b551-f6016e563076}" -json
```

返回 `{"OperationResult":0}`。

重启后，`CiTool --list-policies` 中那条 `AllowMicrosoft_2023-05-04` 已经消失。`Get-Service WinDefend` 显示：

```
Status   Name        DisplayName
------   ----        -----------
Running  WinDefend   Microsoft Defender 防病毒服务
```

随后检查了全部相关服务：

| 服务                    | 状态      |
| ----------------------- | --------- |
| `WinDefend`             | ✅ Running |
| `WdFilter`              | ✅ Running |
| `WdNisSvc`              | ✅ Running |
| `WdNisDrv`              | ✅ Running |
| `SecurityHealthService` | ✅ Running |
| `wscsvc`                | ✅ Running |

`WdBoot` 显示 `Stopped`，这是正常的——它是启动期驱动程序，进入系统后停止运行是预期行为。

### 5.3 确认 EFI 分区没有“后手”

`AllowMicrosoft_2023-05-04` 的一个已知特性是**可能在重启后复活**。微软社区的反馈明确指出，如果只在系统分区删除了 `SiPolicy.p7b`，但 EFI 系统分区中仍留有副本，Windows 启动时会重新加载它。

因此我挂载 EFI 分区进行了检查：

```powershell
mountvol S: /s
Get-ChildItem -Path "S:\EFI\Microsoft\Boot" -Filter "*.p7b" -Recurse
Get-ChildItem -Path "S:\EFI\Microsoft\Boot\CiPolicies\Active"
mountvol S: /d
```

结果：EFI 分区中**没有** `a244370e` 对应的策略文件。列出的 `winsipolicy.p7b` 和几个 `.cip` 均属于 Windows 自身的合法组件（S 模式策略和 Lockdown 策略）。恶意策略的持久化副本并不在 EFI 层。

---

## 六、技术复盘：这次攻击“高级”在哪里

回头看，这次感染之所以让人一度束手无策，原因在于攻击者没有和 Defender“正面冲突”，而是**借用了 Windows 自己的安全机制来废掉 Defender**。

正常的杀毒软件对抗逻辑是：恶意代码尝试运行 → 杀软拦截。但 WDAC 的加载顺序在 Defender 之前。攻击者把恶意策略放进 `CodeIntegrity` 目录，系统在启动早期加载这条策略，将 Defender 的可执行文件标记为“不允许运行”。等到 `WinDefend` 尝试启动时，**操作系统本身已经在执行恶意策略的指令**，拒绝加载 Defender 的核心进程。安全中心 UI 上显示“威胁服务已停止”，但根因不在 Defender 本身，而在它**上面那一层**——WDAC。

这也是为什么 `SFC` 和 `DISM` 修复了系统文件损坏，却对服务启动毫无帮助：文件本身是好的，签名也是有效的，拦截发生在策略层，而不是文件层。

`CiTool` 之所以有效，是因为它直接操作 **WDAC 策略存储**，把那条未签名策略从“已部署策略”列表中移除，而不是和它控制下的文件系统路径较劲。微软官方文档确认，自 Windows 11 2022 更新起，`CiTool.exe -rp` 是移除 WDAC 策略的标准方式，执行后**必须重启**才能让策略停止生效。

## 七、教训与后续

### 已经完成的

- 恶意 WDAC 策略已移除，Defender 全套核心服务恢复运行。
- EFI 分区已检查，未发现策略持久化副本。
- `SFC` 与 `DISM` 已执行，修复了扫描中发现的系统文件损坏。

### 接下来要做的

- **立即执行一次“完全扫描”** 。策略移除只是解除了对 Defender 的封锁，木马本体是否仍在系统中、是否还有其他持久化机制（计划任务、Run 键、随机命名目录下的可执行文件），必须通过全盘扫描来确认。
- **重启后复查 `CiTool.exe --list-policies`** ，确认 `a244370e` 没有重新出现。
- 如果策略复活，需要进一步清理 EFI 分区中的 `SiPolicy.p7b` 副本以及 `HKLM\SOFTWARE\Policies\Microsoft\Windows\DeviceGuard` 下的部署项。

### 最根本的一条

Silver Fox 这类攻击能够成立，依赖的从来不是多么高深的技术突破，而是一个**没有仔细看的域名**，和一个**觉得“命名有点问题但还是运行了”的瞬间**。安全厂商的建议写得很直白：不要轻信搜索引擎中常用软件的搜索结果，无法判断真假时，认准“官方”认证标签；一旦误点误下，立即对设备做杀毒和安全检查。

风扇转快的那一下，其实就是系统在用最后一点“正常”的能力告诉我：**有东西在背后运行，而你的杀毒软件已经被别人关掉了。**
